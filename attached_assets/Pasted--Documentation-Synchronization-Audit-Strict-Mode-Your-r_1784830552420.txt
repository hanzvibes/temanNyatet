# Documentation Synchronization & Audit (Strict Mode)

Your role is to act as a Senior Software Architect, Technical Writer, and Documentation Auditor.

Your objective is to synchronize every Markdown documentation file with the CURRENT state of the codebase.

## Primary Rule

The source code is the ONLY source of truth.

Never document something unless you can verify it directly from the implementation.

If you cannot verify a statement from the codebase, configuration, migrations, package manager, or repository structure:

- DO NOT guess.
- DO NOT infer.
- DO NOT fabricate.
- Instead, explicitly mark it as "Unable to verify from current codebase."

Accuracy is more important than completeness.

---

## Scope

Audit the entire repository, including but not limited to:

- source code
- package.json
- lock files
- configs
- environment examples
- database migrations
- schema
- API routes
- authentication
- scripts
- CI/CD
- deployment configs
- assets
- project structure

Then synchronize ALL documentation.

Examples:

- README.md
- CHANGELOG.md
- CONTRIBUTING.md
- ARCHITECTURE.md
- API.md
- SECURITY.md
- DEPLOYMENT.md
- docs/**
- memory files
- AI context files
- onboarding docs
- developer guides

---

## Required Tasks

### 1. Audit Existing Documentation

Inspect every Markdown file.

For each document:

- identify outdated sections
- identify missing sections
- identify duplicated content
- identify incorrect instructions
- identify broken links
- identify invalid commands
- identify outdated screenshots references
- identify obsolete architecture

Everything must reflect the current implementation.

---

### 2. Verify Every Statement

Every technical statement must be verified against:

- implementation
- configuration
- package manager
- dependencies
- scripts
- routes
- types
- migrations

If not verifiable:

Do not include it.

---

### 3. Remove Hallucinated Content

Delete documentation describing:

- features that do not exist
- APIs that do not exist
- commands that do not work
- configuration that no longer exists
- environment variables that are unused
- deprecated workflows
- speculative future features

---

### 4. Document Missing Information

Only document information that actually exists.

Possible examples:

- project overview
- architecture
- folder structure
- feature list
- authentication flow
- authorization
- API endpoints
- database schema
- migrations
- environment variables
- setup
- installation
- deployment
- scripts
- testing
- build process
- developer workflow
- troubleshooting

Only if implemented.

---

### 5. Preserve Style

Do not completely rewrite documentation unless necessary.

Preserve:

- formatting
- writing style
- heading hierarchy

Improve clarity where appropriate.

---

### 6. Cross-Reference

Ensure every documentation file is internally consistent.

README must agree with:

- architecture docs
- API docs
- deployment docs
- setup docs
- developer guides

No contradictions.

---

### 7. Generate CHANGELOG.md

If CHANGELOG.md does not exist:

Create it.

If it exists:

Append a new entry.

Include:

## Documentation Update

Date:
Repository Version (if detectable):

### Added

### Updated

### Fixed

### Removed

### Deprecated

### Known Limitations

Only include changes actually made.

---

### 8. Produce Documentation Audit Report

Create a report containing:

- Files audited
- Files modified
- Files skipped
- Files created
- Documentation coverage
- Outdated sections removed
- Broken links fixed
- Invalid commands fixed
- Missing docs discovered
- Unverifiable items
- Remaining documentation debt
- Recommendations

---

## Safety Rules

Never invent:

- architecture
- APIs
- database tables
- environment variables
- endpoints
- authentication flows
- scripts
- deployment steps

Never claim something is implemented unless you have verified it.

Never fabricate examples.

Never fabricate code snippets.

Never fabricate diagrams.

Never fabricate changelog entries.

---

## Before Editing Any Documentation

For every change ask yourself:

"Can I point to the exact implementation that proves this?"

If the answer is NO:

Do not write it.

---

## Final Validation Checklist

Before finishing:

- Every command has been verified.
- Every path exists.
- Every file reference exists.
- Every environment variable exists.
- Every API exists.
- Every script exists.
- Every dependency exists.
- Every documented feature exists.
- Every removed feature has been removed from documentation.
- README matches the current project.
- CHANGELOG has been updated.
- Documentation contains zero speculative content.

The final documentation should be a faithful representation of the current repository, not assumptions about how the project should work.
